## 二、执行效率（页面响应）

### 2.1 实测结果

| 页面 | 路由 | 中位数 | 平均 | P95 | 最大 |
| --- | --- | --- | --- | --- | --- |
| 登录页 | `/login` | 0.91 ms | 0.89 ms | 1.05 ms | 1.10 ms |
| 学生首页 | `/student/index` | 1.64 ms | 1.74 ms | 2.14 ms | 3.16 ms |
| 浏览题库 | `/student/browse` | 1.85 ms | 2.02 ms | 2.94 ms | 3.36 ms |
| 我的选题 | `/student/mine` | 1.54 ms | 1.78 ms | 2.21 ms | 4.68 ms |
| 结果公示 | `/student/public` | 1.40 ms | 1.53 ms | 1.95 ms | 2.97 ms |
| 站内通知 | `/student/notices` | 1.37 ms | 1.75 ms | 2.02 ms | 10.35 ms |
| 教师工作台 | `/teacher/index` | 1.93 ms | 1.99 ms | 2.61 ms | 2.73 ms |
| 选题监控 | `/teacher/monitor` | 1.90 ms | 2.15 ms | 3.09 ms | 3.29 ms |
| 题库维护 | `/teacher/topics` | 1.73 ms | 1.79 ms | 1.97 ms | 3.09 ms |
| 选题轮次 | `/teacher/round` | 1.39 ms | 1.59 ms | 2.49 ms | 2.74 ms |
| 我的学生 | `/teacher/students` | 2.02 ms | 2.54 ms | 3.58 ms | 12.75 ms |
| 操作日志 | `/teacher/logs` | 1.34 ms | 1.51 ms | 2.37 ms | 2.73 ms |
| CSV 导出 | `/teacher/export` | 1.24 ms | 1.39 ms | 2.00 ms | 2.33 ms |
| 用户管理 | `/admin/users` | 3.49 ms | 4.20 ms | 5.50 ms | 13.36 ms |

**结论**：14 个页面/接口服务端处理中位数 0.91~3.49 ms，最慢的「用户管理」也不到 4 ms，全部明显低于 100 ms 的交互流畅阈值。

### 2.2 登录耗时单独说明

| 角色 | 登录往返 |
| --- | --- |
| 学生 | 84.39 ms |
| 教师 | 76.43 ms |
| 管理员 | 77.26 ms |

登录比普通页面慢约 80 ms，是**有意为之的安全成本**：Werkzeug 3 默认用 scrypt（`scrypt:32768:8:1`）做密码哈希校验，单次约 70~80 ms，可显著提高离线爆破成本。这个量级用户无感。

### 2.3 效率来自哪里

- SQLite 开启 **WAL**：读写不互相阻塞，查询走内存页缓存；
- 为高频条件建索引：`(TOPIC_ID, STATUS)`、`(ROUND_ID, OPERATED_AT)`、`(USER_ID, READ_FLAG)`、`(USER_ID)`；
- 页面只做必要的聚合查询（选题数按 `GROUP BY TOPIC_ID` 一次取回，避免 N+1）；
- 操作日志页 `LIMIT 300`，避免全表扫描渲染；
- 无前端框架与打包产物，服务端渲染直出，首屏无 JS 阻塞。

## 三、并发安全（现场重点）

### 3.1 实测

```
T03 人数上限: 2，6 人并发抢题
结果: 已确认 2 人, 候补 4 人
PASS: 未超卖（确认数 2 <= 上限 2），候补队列正常
```

多用户 E2E 中另有一组：A 班 4 人并发抢上限 2 的课题，结果恰好 2 人确认、2 人候补，最终全库无超卖、无学生重复确认（22 项断言通过）。

### 3.2 为什么不会超卖

| 机制 | 作用 |
| --- | --- |
| `BEGIN IMMEDIATE` | 抢题开始时立即取写锁，把「查人数 → 插入」串行化，杜绝检查与写入之间的竞态 |
| 事务内计数 | 容量判断与插入在同一事务，读到的就是最新已确认数 |
| 部分唯一索引 `(ROUND_ID, USER_ID) WHERE STATUS='confirmed'` | 数据库层兜底：同一轮一人最多一条已确认记录，重复插入直接失败 |
| `sqlite3.IntegrityError` 捕获 | 冲突时回滚并提示，不产生 500 |
| WAL + 30s busy timeout | 并发写排队等待，不立即报「database is locked」 |

### 3.3 现场演示（30 秒）

```bash
cd student-topic-system/src
python ../tests/test_concurrent_select.py
```

预期看到「已确认 2 人, 候补 4 人」与 `PASS: 未超卖`。

## 四、安全性

### 4.1 机制与证据

| 威胁 | 措施 | 证据/现场验证 |
| --- | --- | --- |
| 任意注册、冒名选课 | 不开放注册，仅管理员登记；登录同时校验 `FLAG=1` 与 `STATUS='active'` | 用 `nobody` 登录被拒；停用账号被拒 |
| 密码泄露 | Werkzeug scrypt 哈希存储，不存明文 | 库中为 `scrypt:32768:8:1$...`，反推不出原密码 |
| CSRF 伪造请求 | 会话级随机令牌，所有表单隐藏域携带；`before_request` 用 `hmac.compare_digest` 校验 | 删除隐藏域提交 → 「表单校验失败（CSRF）」 |
| SQL 注入 | 334 处 `?` 参数化占位；仅有的 2 处 f-string 用于内部表名/固定列名迁移，不接收用户输入 | 搜索 `' OR 1=1 --` 返回空列表且无报错 |
| XSS | Jinja2 默认开启自动转义；仅 CSRF 隐藏域使用受控 `Markup` | 模板中所有用户数据均经 `{{ }}` 转义输出 |
| 垂直越权 | `@login_required("role")` 装饰器 | 学生访问教师端/管理员页 → 「无权限访问」 |
| 水平越权 | 所有查询带归属条件：教师 `TEACHER_ID=当前用户`，学生 `ADVISOR_ID=自己的导师` | 教师2 打开教师1 的退课链接 → 「无权操作他人课题的记录」 |
| 会话固定 | 登录成功后 `session.clear()` 再写入身份，旧会话内容不继承 | 登录后仅保留新的身份字段与 CSRF 令牌 |
| 误删数据 | 业务表统一带 `FLAG` 软删除标记，删除只置 `FLAG=0`；有选题记录的课题/用户禁止删除 | 删除后列表不可见，历史记录仍可查 |

### 4.2 已知安全边界（主动说明，避免被问倒）

| 项 | 现状 | 生产化改进 |
| --- | --- | --- |
| 登录提示 | 区分「账号不存在」与「密码错误」 | 统一为「账号或密码错误」+ 登录限流 |
| 密钥 | `secret_key` 写在代码中 | 改为环境变量/密钥管理 |
| 运行模式 | `debug=True` 便于课设演示 | 生产关闭 debug，改用 gunicorn/waitress |
| 登录限流 | 无 | 加失败次数锁定或验证码 |
| 审计防篡改 | 日志可被数据库管理员修改 | 日志哈希链或外部审计库 |

> 这些是课程项目范围内的取舍，不作为功能缺陷；主动说明能体现工程判断。

## 五、报错处理（不抛裸异常、不出现 500）

`app.py` 中共 **94 处** `flash` 提示，其中 **69 处**为错误分支；关键写操作均有 `try/except` + 回滚。

### 5.1 异常路径抽查（2026-10-30 实测）

| 触发方式 | 实际响应 | 是否 500 |
| --- | --- | --- |
| 未登录访问 `/teacher/monitor` | 302 跳转登录页 | 否 |
| 学生访问 `/teacher/index` | 「无权限访问」并回学生首页 | 否 |
| 删除表单 `_csrf_token` 后提交 | 「表单校验失败（CSRF），请返回页面重试」 | 否 |
| POST `/student/select/99999` | 「题目不存在、已关闭或不属于你的指导教师」 | 否 |
| GET `/teacher/kick/99999` | 「记录不存在或状态不允许退课」 | 否 |
| POST 退选不存在的记录 | 「记录不存在或状态不允许退选」 | 否 |
| 改密两次输入不一致 | 「两次输入的新密码不一致」 | 否 |
| 访问不存在的路由 `/nope` | 404 默认页 | 否 |
| GET 调用只允许 POST 的选题接口 | 405 Method Not Allowed | 否 |
| 管理员删除管理员账号 | 「不能删除管理员账号」 | 否 |

### 5.2 事务与回滚

选题、志愿提交、分配、抽签、退课、退选均在事务中执行；任一步失败即 `ROLLBACK` 并给出中文提示。抽签曾因「一人多题同时中签」触发唯一索引导致整批回滚，已通过 BUG-04 修复（全局已中签集合），并有回归断言防复发。

## 六、健壮性

| 维度 | 做法 | 现场可验证 |
| --- | --- | --- |
| 输入校验 | 必填、长度、数值范围（成绩 0~100、绩点 0~5、志愿序号 1~MAX_WISH） | 填 6 绩点 → 提示越界 |
| 表单防篡改 | 志愿数据服务端二次解析；题目必须属于本人导师、面向本班、处于开放窗口 | 改志愿序号为 9 → 拒绝且不写入 |
| 重复提交 | 一人一轮仅一条有效记录；部分唯一索引兜底 | 再点选题 → 「每人限选 1 题」 |
| 状态机约束 | 只有 confirmed/waiting 可退选；只有 wish/entry/waiting 可撤销；已取消记录不可重复操作 | 退选后再退 → 提示状态不允许 |
| 关联一致性 | 有选题记录的课题不可删除、有记录的用户不可删除，只能关闭/停用 | 删除 T01 → 提示不能删除 |
| 数据保留 | 退选不删除记录，状态置 `cancelled` 并记 `CANCELLED_AT`；每次状态变化追加日志 | 我的选题「历史记录」可查 |
| 并发异常 | 唯一索引冲突被捕获并回滚，不向前端抛栈 | 并发脚本 6 抢 2 无 500 |
| 软删除 | `FLAG` 标记，列表过滤，历史与统计不受影响 | 库中 `FLAG=0` 可查 |

## 七、可维护性与可追溯性（加分项）

| 项 | 现状 |
| --- | --- |
| 数据规范 | 9 张表统一 `CREATED_BY / CREATED_AT / UPDATED_BY / UPDATED_AT / FLAG` 五公共字段，审计与软删除一致 |
| 日志留痕 | `SELECTION_EVENTS` 记录 select/cancel/kick/promote/allocate/lottery，含操作人、前后状态、志愿/候补号、原因与抽签种子 |
| 数据库演进 | `db.py::migrate()` 为老库补列/补表，升级不丢历史数据 |
| 配置集中 | 策略名、状态名、退选原因白名单集中在 `app.py` 顶部常量，改文案不改逻辑 |
| 部署简单 | 无外部服务依赖，`pip install -r requirements.txt && python app.py` 即跑 |
| 权限模型 | 管理员只管账户、教师只管自己的课题与轮次、学生只看本导师课题，职责边界清晰 |

## 八、现场演示脚本（每个 30~60 秒）

### 演示 1：并发不超卖（命令行）

```bash
cd student-topic-system/src
python ../tests/test_concurrent_select.py
```

讲解词：6 个线程同时抢一个上限 2 的课题，事务串行化 + 唯一索引兜底，最终恰好 2 人确认、4 人候补，零超卖。

### 演示 2：越权与 CSRF（浏览器）

1. 学生窗口地址栏输入 `/teacher/index` → 「无权限访问」；
2. 在选题表单上右键「检查」，删掉隐藏的 `_csrf_token`，点提交 → 「表单校验失败（CSRF）」；
3. 教师窗口访问 `/admin/users` → 「无权限访问」。

讲解词：垂直越权靠角色装饰器，水平越权靠每次查询带归属条件，CSRF 靠会话令牌。

### 演示 3：错误路径与日志（浏览器）

1. 教师窗口访问 `/teacher/kick/99999` → 友好提示，无异常栈；
2. 打开「操作日志」，按动作筛选「退选/递补/抽签」→ 每次状态变化都有记录，抽签备注含种子。

讲解词：错误一律转成中文提示并回滚；所有关键动作留痕，可追溯到人、时间、前后状态。

## 九、结论

| 维度 | 结论 |
| --- | --- |
| 效率 | 14 个页面/接口中位数 0.91~3.49 ms，登录 76~84 ms 为 scrypt 安全成本 |
| 安全性 | 登记制 + scrypt + CSRF + 参数化 + 双重权限校验，常见攻击面均有对应措施 |
| 报错 | 69 处错误分支，抽查 10 条异常路径均无 500、无裸异常 |
| 健壮性 | 输入/状态/关联/并发/重复提交均有约束，失败可回滚且数据可追溯 |
