## 二、PPT 逐页大纲与口播稿

### 第 1 页｜封面

- 画面：项目名「TopicGo 学生选题系统」、副标题「《软件工程》课程设计验收」、成员、日期 2026-10-31。
- 口播（15 秒）：
  > 老师好，我们是第 X 组，项目是学生选题系统 TopicGo。下面按验收表的四个维度汇报：功能、非功能、关键技术、工作量。

### 第 2 页｜验收四维度

- 画面：四栏卡片：功能展示 / 非功能性 / 关键技术 / 工作量，各配一句证据。
- 口播（20 秒）：
  > 汇报顺序对应验收表：功能展示有 61 条用例和三套自动化测试；非功能有实测数据；技术讲框架与数据组织；工作量报主体代码 3917 行。

### 第 3 页｜背景与目标

- 画面：三个痛点（顺序不透明、名额易超卖、统计靠手工）→ 三个目标（公平、防超卖、可追溯）。
- 口播（40 秒）：
  > 传统课设选题靠群里接龙或表格，谁先谁后不透明，名额容易超卖，最后统计靠手工。
  > 我们做了三件事：把规则写进系统，支持四种公平策略；用事务和唯一索引保证多人同时抢不超卖；所有动作写日志，退选也不删记录，随时可审计。

### 第 4 页｜角色与功能地图

- 画面：三列：管理员（只登记账户）、教师（只管自己的课题/轮次/学生）、学生（只看本导师课题）。
- 口播（35 秒）：
  > 系统有三个角色，职责严格分开。管理员不碰课程业务，只登记账号、分配导师、停用和重置密码；教师只能管理自己发布的课题和自己的轮次，只能看到自己的学生；学生只能看到自己导师开放的课题，看不到别的老师的数据。
  > 这样做的好处是权限边界清晰，任何越权访问都会被拦截。

### 第 5 页｜四种选题策略

- 画面：表格：先到先得 / 绩点优先 / 多志愿 / 随机抽签；每行：学生动作、录取规则、适用场景。
- 口播（45 秒）：
  > 一轮选题可以用四种策略。先到先得拼手速；绩点优先会拦住低绩点同学，等高绩点先选；多志愿是平行志愿，按志愿序处理，同志愿超员按绩点，没命中第一志愿转候补；随机抽签用公开种子洗牌，同一种子和同一名单可以复现结果，每人最多中一题。
  > 策略是轮次级配置，老师随时能切换，不用改代码。

### 第 6 页｜系统截图（功能一览）

- 画面：左：学生浏览题库（6 个课题、前置要求、已选/剩余）；右：教师工作台（班级、进度、未选题红色标记）。
- 口播（30 秒）：
  > 左边是学生端题库，能看到前置要求、已选和剩余名额，只能看到自己导师的课题；右边是教师工作台，按班级看选题进度，红色是还没选的学生，下面是待办统计。

### 第 7 页｜功能测试与结果

- 画面：三行结果：回归 126 通过 / E2E 22 通过 / 并发 PASS；右侧 61 条手工用例与 8 类场景。
- 口播（40 秒）：
  > 测试分三层：126 项全功能回归，覆盖权限、留痕、候补、志愿、抽签、CSRF、防反复退选；22 项多用户 E2E，2 位老师 12 名学生 3 个班协同；还有并发脚本，6 个人抢 2 个名额，结果恰好 2 人确认、4 人候补。
  > 另外准备了 61 条手工用例，老师可以现场抽查任意一条。

### 第 8 页｜非功能：效率与并发

- 画面：左：14 个页面/接口响应中位数 0.91~3.49 ms 的小柱图；右：并发测试输出。
- 口播（40 秒）：
  > 效率方面，14 个页面/接口服务端处理中位数都在 1 到 3.5 毫秒，最慢的用户管理不到 4 毫秒；登录要 76 到 84 毫秒，这是 scrypt 密码哈希的安全成本，用户无感。
  > 并发方面，6 个线程抢 2 个名额，确认数严格等于 2，没有超卖，候补队列也正确。

### 第 9 页｜非功能：安全与健壮

- 画面：四组关键词：登记制 + scrypt；CSRF + 参数化；角色 + 归属双重校验；69 处错误分支 + 事务回滚。
- 口播（40 秒）：
  > 安全上，不开放注册，只有管理员登记的账号能登录；密码用 scrypt 哈希；所有表单带 CSRF 令牌；SQL 全部参数化；权限除了角色装饰器，每次查询还带导师或教师的归属条件，防水平越权。
  > 健壮性上，69 处错误分支全部转成中文提示，写操作失败自动回滚；我们抽查了 10 条异常路径，没有出现 500，也没有裸异常栈。

### 第 10 页｜技术栈与架构

- 画面：分层图：浏览器 → Flask 路由（33 条）→ 业务函数 → db.py → SQLite（9 表）。
- 口播（35 秒）：
  > 技术栈是 Python 3.12 + Flask 3 + Jinja2 + SQLite，服务端渲染，没有前端构建链，一条命令就能跑。
  > 架构分四层：路由、业务、数据访问、SQLite；所有写操作都是校验、事务、写业务表、写日志、提交。

### 第 11 页｜数据组织

- 画面：9 张表清单 + 五公共字段 + 6 个索引（标红两个部分唯一索引）。
- 口播（40 秒）：
  > 数据库 9 张表，所有表统一五个公共字段：创建人、创建时间、修改人、修改时间、软删除标记。
  > 最关键的是两个部分唯一索引：同一轮一个学生只能有一条已确认记录，同一学生同一课程只有一条成绩。这两个索引是并发防重和数据一致性的最后一道保险。

### 第 12 页｜关键实现

- 画面：左侧 `BEGIN IMMEDIATE` 伪代码；右侧抽签种子与洗牌。
- 口播（40 秒）：
  > 抢题先用 BEGIN IMMEDIATE 拿写锁，把查人数和插入串行化，事务里判断容量，满了转候补，最后唯一索引兜底。
  > 抽签先把报名按固定键排序，保证输入顺序确定，再用公开种子洗牌；种子写进每条日志，任何人拿同样的种子和名单都能复现结果。

### 第 13 页｜工作量

- 画面：大数字 3917；拆分：后端 1972 + SQL 171 + 模板 1595 + 样式 179；旁边注明测试 1142、文档 2066 不计入。
- 口播（40 秒）：
  > 主体功能代码 3917 行，其中后端 1972 行、数据库脚本 171 行、页面模板 1595 行、样式 179 行。
  > 测试脚本 1142 行、文档 2066 行按要求不计入。所有数字都可以用 wc -l 当场复核。

### 第 14 页｜分工与进度

- 画面：两人卡片：各 16 项任务；时间线：立项 → 需求 → 设计 → 实现 → 测试 → 发布。
- 口播（30 秒）：
  > 小组两人，32 项任务各 16 项。我负责架构、数据库、核心算法和测试；他负责需求、原型、前端页面和文档发布。开发和测试并行，测试发现问题由另一人复现修复，避免自己测自己。

### 第 15 页｜总结与改进

- 画面：三条结论 + 三条改进 + Q&A。
- 口播（25 秒）：
  > 总结：功能完整、并发安全、过程可追溯，三套测试全部通过。
  > 不足也很明确：密钥和 debug 需要生产化，登录没有限流，SQLite 是单机方案。如果扩展到全校，会换 PostgreSQL、加 Redis 锁和分页缓存。
  > 以上，请老师提问。

## 四、预设问答（背要点即可）

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 SQLite，不用 MySQL？ | 课程规模百人级，SQLite 单文件、零运维、便于演示；已开 WAL，读写不互斥；数据访问集中在 `db.py`，换 PostgreSQL 只改连接与少量 SQL。 |
| 多人同时抢，怎么保证不超卖？ | `BEGIN IMMEDIATE` 立即写锁把「查人数 + 插入」串行化；事务内判断容量；部分唯一索引 `(ROUND_ID, USER_ID) WHERE confirmed` 兜底；实测 6 抢 2 零超卖。 |
| 抽签真的公平吗？ | 种子公开并写入每条日志；报名先按固定键排序保证输入顺序确定，再用 `random.Random(seed).shuffle`；同种子同名单结果可复现；每人最多中 1 题。 |
| 学生反复退选、恶意占名额怎么办？ | 每轮退选次数上限、截止前 N 小时禁退、退选原因白名单并写日志；教师撤销不计入学生次数；退选后按策略自动/手动递补。 |
| 怎么防水平越权？ | 每次查询都带归属条件：教师 `TEACHER_ID=当前用户`，学生 `ADVISOR_ID=自己的导师`；改 ID 也查不到别人的数据。 |
| 退选后记录还在吗？ | 不删除，状态置 `cancelled` 并记录时间；我的选题有历史记录，日志可查，统计不受影响。 |
| 代码量怎么算的？ | `wc -l` 统计；主体功能 3917 行 = 后端 1972 + SQL 171 + 模板 1595 + 样式 179；测试 1142、文档 2066 不计入，可当场复核。 |
| 项目最难的点？ | 并发与策略切换：规则从先到先得切到多志愿时不能超分配；抽签一人多题会触发唯一索引导致整批回滚（BUG-04），用全局已中签集合解决并加回归断言。 |
| 测试用例怎么设计的？ | 等价类 + 边界值 + 异常路径 + 并发：正常流程、越权、非法 ID、篡改表单、重复提交、次数/时间边界，再加 6 线程并发。 |
| 有什么不足？ | 密钥硬编码、debug 模式、无登录限流、SQLite 单机、无分页；生产化会改环境变量、关 debug、加限流与 PostgreSQL/Redis。 |
| 切换规则后之前的志愿怎么办？ | 有未处理志愿/报名时禁止切换规则；若已是历史遗留，监控页会出现「处理遗留志愿/报名」，可一次性按原策略处理，或逐条撤销后让学生重选。 |
| 成绩怎么录？ | 我的学生 →「成绩/绩点录入」会同时展开两个表单：课程名 + 分数（可填学期）和绩点；课程成绩用于前置核验与志愿分配。 |
| 如果两个老师开同一门课？ | 课题归属教师，学生只看自己导师的课题；轮次也按教师隔离；跨教师数据在查询层就过滤掉。 |
| 为什么不用 Vue/React？ | 18 个页面、交互简单，服务端渲染首屏快、无构建链、部署只需 Python；把复杂度留给业务与并发，而不是工程链。 |

## 五、风险预案

| 风险 | 处理 |
| --- | --- |
| 5000 端口被占用 | `lsof -i :5000` 找到进程结束，或临时改 `app.run(port=5001)` |
| 依赖未安装 | `cd src && pip install -r requirements.txt`；或用已装好的虚拟环境 |
| 演示数据被测试污染 | 停服务 → 删 `topicgo.db*` → 重启，恢复 7 账号/6 课题/1 轮次 |
| 现场测试失败 | 先确认在 `src` 目录、服务已启动；仍失败则展示本文档记录的实测输出与截图，不纠缠 |
| PPT 字体缺失 | 全文使用「微软雅黑」，Windows/Office 默认可用；放映前在本机预览一遍 |
| 投屏比例不对 | 浏览器 F11 全屏、缩放 100%；PPT 16:9 |
| 时间被压缩到 3 分钟 | 讲第 1、5、6、8、13 页 + 跑并发脚本 + 一句总结 |

## 六、答辩时的三条底线

1. **不夸大**：数字说实测值，不把「约」说成精确值；不确定的就说「回归脚本覆盖，现场可以跑」。
2. **不回避**：被问不足，主动说密钥、debug、限流、单机，再给改进方案，比辩解加分。
3. **不空讲**：每个结论都落到一个页面、一条日志或一次脚本输出。
