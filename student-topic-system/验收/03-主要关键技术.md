## 二、系统架构

### 2.1 分层

```
┌────────────────────────────────────────────────────────┐
│  浏览器（学生 / 教师 / 管理员，PC + 手机自适应）        │
└───────────────┬────────────────────────────────────────┘
                │ HTTP + Session Cookie + CSRF Token
┌───────────────▼────────────────────────────────────────┐
│  Flask 路由层  app.py（33 个 URL 规则）                 │
│  ├─ 认证与权限：login_required / session / 角色校验      │
│  ├─ 学生端：browse / select / wish / cancel / mine …    │
│  ├─ 教师端：topics / round / monitor / allocate / …     │
│  ├─ 管理端：users（仅账户，不碰课程业务）                │
│  └─ 通用：password / 项目主页 / 原型 / 流程展示          │
├────────────────────────────────────────────────────────┤
│  业务函数层（策略、递补、前置核验、日志、CSV）           │
├────────────────────────────────────────────────────────┤
│  数据访问层  db.py（连接、WAL、初始化、迁移、种子）       │
├────────────────────────────────────────────────────────┤
│  SQLite  topicgo.db（9 张表 + 6 个索引，单文件）         │
└────────────────────────────────────────────────────────┘
```

### 2.2 一次请求的处理链

以「学生选题」为例：

1. `POST /student/select/<topic_id>` 进入路由；
2. `@login_required("student")` 校验登录与角色；
3. `before_request` 校验 CSRF 令牌；
4. 读取当前轮次，校验时间窗口、班级范围、规则模式、师生归属、前置要求；
5. `BEGIN IMMEDIATE` 开启事务，统计已确认人数并插入记录；
6. 写 `SELECTION_EVENTS` 日志，`COMMIT`；
7. 重定向回题库页，Flash 提示结果。

**设计要点**：所有写操作都是「校验 → 事务 → 写业务表 → 写日志 → 提交」，任一步失败整体回滚。

## 三、数据组织

### 3.1 九张表

| 表 | 作用 | 关键字段 | 关系 |
| --- | --- | --- | --- |
| `USERS` | 用户（学生/教师/管理员） | USER_NO、USER_NAME、PASSWORD_HASH、ROLE、ADVISOR_ID、GPA、STATUS | 学生 → 教师（ADVISOR_ID） |
| `TOPICS` | 课题 | TOPIC_CODE、MAX_NUM、TEACHER_ID、TARGET_CLASSES、PREREQ_RULES、STATUS | 教师 1:N 课题 |
| `ROUNDS` | 选题轮次与策略 | RULE、START_AT、END_AT、PROMOTE_MODE、MAX_WISH、LOTTERY_SEED、MAX_CANCEL | 教师 1:N 轮次 |
| `SELECTIONS` | 选题/志愿/候补记录 | ROUND_ID、TOPIC_ID、USER_ID、STATUS、WISH_NO、QUEUE_NO | 轮次/课题/学生 三者关联 |
| `SELECTION_EVENTS` | 操作日志（只追加） | ACTION、FROM_STATUS、TO_STATUS、OPERATOR、REMARK、OPERATED_AT | 关联轮次/课题/学生 |
| `COURSES` | 课程字典 | COURSE_NAME、CREDIT | — |
| `SCORES` | 学生课程成绩 | USER_ID、COURSE_ID、SCORE、TERM | 学生 + 课程 |
| `NOTICES` | 站内通知（退课提醒） | USER_ID、TITLE、CONTENT、KIND、READ_FLAG | 学生 1:N 通知 |
| `ANNOUNCEMENTS` | 教师公告 | TITLE、CONTENT、TEACHER_ID | 教师 1:N 公告 |

### 3.2 统一五公共字段

所有业务表都含：

| 字段 | 含义 |
| --- | --- |
| `CREATED_BY` / `CREATED_AT` | 创建人与时间 |
| `UPDATED_BY` / `UPDATED_AT` | 最后修改人与时间 |
| `FLAG` | 软删除标记（1 有效 / 0 已删） |

好处：审计口径统一、删除可追溯、迁移与统计简单。

### 3.3 显式索引与约束（共 6 个）

| 名称 | 类型 | 作用 |
| --- | --- | --- |
| `UK_SELECTION_USER` | 部分唯一索引 `(ROUND_ID, USER_ID) WHERE STATUS='confirmed'` | 同一轮一人最多一条已确认记录（并发防重兜底） |
| `UK_SCORE_USER_COURSE` | 部分唯一索引 `(USER_ID, COURSE_ID) WHERE FLAG=1` | 同一学生同一课程只保留一条成绩 |
| `IDX_SELECTION_TOPIC` | 普通索引 `(TOPIC_ID, STATUS)` | 加速按题统计已选/候补人数 |
| `IDX_EVENTS_ROUND` | 普通索引 `(ROUND_ID, OPERATED_AT)` | 加速按轮次按时间查日志 |
| `IDX_SCORES_USER` | 普通索引 `(USER_ID)` | 加速查学生成绩 |
| `IDX_NOTICES_USER` | 普通索引 `(USER_ID, READ_FLAG)` | 加速未读通知计数 |

> 另有 `USER_NO`、`USER_NAME`、`TOPIC_CODE`、`COURSE_NAME` 的 UNIQUE 约束，SQLite 会自动建索引，未计入上述 6 个显式索引。

### 3.4 选题状态机

```
                  ┌──────────── 退选/撤销/退课 ────────────┐
                  ▼                                        │
             cancelled（保留记录，不物理删除）               │
                                                           │
  first_come/gpa_priority:  select → confirmed ──满员──→ waiting（候补）
  multi_wish:               submit → wish ──分配命中──→ confirmed
                                       ├─ 未命中第一志愿 → waiting
                                       └─ 未命中其他志愿 → cancelled
  lottery:                  报名 → entry ──中签──→ confirmed
                                     ├─ 未中签 → waiting
                                     └─ 已在其他题中签 → cancelled
```

状态含义：`confirmed` 已确认 / `waiting` 候补中 / `wish` 志愿待分配 / `entry` 已报名待抽签 / `cancelled` 已取消（退选/撤销/退课）。

## 四、关键实现

### 4.1 并发选题不超卖

位置：`src/app.py` 学生选题路由。

```python
conn.execute("BEGIN IMMEDIATE")          # 1. 立即取写锁，串行化并发抢题
confirmed = conn.execute(
    "SELECT COUNT(*) c FROM SELECTIONS"
    " WHERE ROUND_ID=? AND TOPIC_ID=? AND STATUS='confirmed'",
    (rnd["ID"], topic_id)).fetchone()["c"]
if confirmed < topic["MAX_NUM"]:         # 2. 事务内判断容量
    conn.execute("INSERT INTO SELECTIONS(...STATUS='confirmed'...)")  # 3. 写入
    log_event(...)                        # 4. 同事务写日志
    conn.execute("COMMIT")
elif rnd["WAITLIST_ON"]:
    ...                                   # 5. 满员转候补，编号 MAX+1
```

数据库层再用部分唯一索引兜底；`sqlite3.IntegrityError` 被捕获后回滚并提示。这样「检查 + 插入」不会交错，6 并发抢 2 名额实测零超卖。

### 4.2 四种公平策略（策略模式）

| 策略 | RULE | 学生动作 | 录取规则 | 适合场景 |
| --- | --- | --- | --- | --- |
| 先到先得 | `first_come` | 直接选题 | 按提交时间，满员转候补 | 拼手速、简单直接 |
| 绩点优先 | `gpa_priority` | 直接选题 | 仍有更高绩点同学未选时拒绝，最高绩点先选 | 成绩导向 |
| 多志愿分配 | `multi_wish` | 填 1~N 个志愿 | 按志愿序依次处理，同志愿超员按绩点；未命中第一志愿转候补 | 兼顾意愿与公平 |
| 随机抽签 | `lottery` | 报名（可多题） | 公开种子洗牌，每人最多中 1 题 | 完全随机、可审计 |

策略由轮次配置 `ROUNDS.RULE` 驱动，切换策略无需改代码；教师可在「选题轮次」页随时调整。

### 4.3 多志愿分配

- 先按 `WISH_NO` 升序、`GPA` 降序遍历所有志愿；
- 维护每题「已确认数」快照，避免与先到先得阶段叠加导致超分配；
- 命中即 `confirmed`，并记录「第 N 志愿命中」日志；
- 一人只命中一次，其余志愿置 `cancelled` 并留痕；
- 第一志愿落空 → `waiting` 候补；非第一志愿落空 → 作废；
- 课题已关闭 → 该志愿作废，不占用分配结果。

### 4.4 随机抽签可复现

```python
seed = rnd["LOTTERY_SEED"] or f"{rnd['ID']}-{rnd['ROUND_NAME']}"
rng = random.Random(seed)
entries.sort(key=lambda e: (-e["GPA"], e["ID"]))  # 固定输入顺序
rng.shuffle(entries)                               # 洗牌
```

关键点：

1. **种子公开**：写入每次抽签日志的 `REMARK`，任何人可查；
2. **输入顺序确定**：先按固定键排序，避免数据库返回顺序影响结果；
3. **算法确定**：`random.Random(seed)` 在同一 Python 版本下结果可复现；
4. **一人一题**：全局已中签集合，重复报名只保留一题，其余作废并留痕（BUG-04 修复）。

### 4.5 退选与递补

- 退选三重防护：每轮次数上限（`MAX_CANCEL`）、截止前锁定（`CANCEL_LOCK_HOURS`）、原因白名单（4 项，写入日志）；
- 退选不删记录：状态置 `cancelled`，保留 `CANCELLED_AT`；
- 递补三种模式：`auto` 候补首位自动递补 / `manual` 教师点「递补」/ `off` 不递补；
- 教师撤销（revoke）不计入学生退选次数，学生可重新提交。

### 4.6 前置要求核验

- 课题侧：`PREREQ_TEXT`（人话描述，学生可见）+ `PREREQ_RULES`（JSON，如 `{"数据结构": 75}`）；
- 成绩侧：`COURSES` + `SCORES`，教师按自己的学生录入/更新；
- 学生浏览时逐题核验：满足显示「✅」，不满足显示缺失课程与实际分，并在选题确认框二次警告；
- 教师监控页按同一规则核验，不满足可一键退课；退课必须填原因与建议，学生收到站内通知，日志保留全文。

## 五、安全技术（实现层）

| 机制 | 实现 |
| --- | --- |
| 身份认证 | Flask Session（签名 Cookie）+ Werkzeug scrypt 哈希 |
| 权限 | `@login_required("student"/"teacher"/"admin")` + 每次查询带 `ADVISOR_ID` / `TEACHER_ID` 归属条件 |
| CSRF | 会话级随机令牌，全部 POST 表单隐藏域携带，`before_request` 常量时间比较 |
| SQL 注入 | 334 处 `?` 参数化占位，无用户输入拼接（仅内部表名/列名迁移使用固定字符串） |
| XSS | Jinja2 自动转义；仅 CSRF 隐藏域使用受控 `Markup` |
| 数据一致性 | 显式事务 + `BEGIN IMMEDIATE` + 部分唯一索引 + 软删除 |
| 审计 | `SELECTION_EVENTS` 只追加，记录动作、前后状态、操作人、原因、种子 |

## 六、设计取舍（答辩常问）

| 决策 | 选择 | 理由 | 若扩展到生产 |
| --- | --- | --- | --- |
| 数据库 | SQLite（WAL） | 单文件、零运维、便于演示与迁移；课程规模（百人级）足够 | 换 PostgreSQL/MySQL，`db.py` 是唯一改动点 |
| 架构 | 服务端渲染单体 | 无前后端分离成本，18 个页面由 1 个进程直出，部署只需 Python | 前后端分离 + REST API + Nginx |
| 数据访问 | 原生 SQL，无 ORM | 表结构与 SQL 在验收时可直接讲清；性能可控 | SQLAlchemy + Alembic 迁移 |
| 并发控制 | 数据库写锁 + 唯一索引 | 单机场景最可靠、最简单，无需 Redis | 分布式锁/消息队列，数据库唯一约束仍保留兜底 |
| 前端 | 原生 CSS + 少量 JS | 无构建链、加载快、手机自适应 | Vue/React + 组件库 |
| 抽签 | 公开种子 + 可复现洗牌 | 公平性可被任何人复核，避免「黑箱」质疑 | 第三方公证/区块链存证 |

## 七、可扩展点

- 新增策略：在 `RULE_NAMES` 与对应分支增加一种规则，前端按 `RULE` 展示入口；
- 新增角色：`USERS.ROLE` + `login_required` 参数即可扩展（如教学秘书）；
- 新增报表：复用 `SELECTIONS` + `SELECTION_EVENTS`，导出 CSV 已有实现；
- 数据迁移：`db.py::migrate()` 已支持补列/补表，老库升级不丢数据。
